# Extensions

How Veyra manages extensions, their SIP credentials and the numbering plan,
and how secrets are protected at rest. Delivered in Milestone 4. Live
registration status and internal calling tests followed in Milestone 5,
device provisioning (which removes the need to type credentials into
phones) in Milestone 9, and where each phone registers from (its source
address, public behind NAT, next to the address the phone reports) in
Milestone 18 ([CALL_FEATURES.md](CALL_FEATURES.md) §2.1).

## 1. What an extension is

An extension is a number that a phone registers with. It belongs to one
organization, may be assigned to a user or be a shared phone (front office,
classroom, hallway), and carries:

| Field | Notes |
|---|---|
| `number` | Digits only, validated against the numbering plan (§2); unique across the installation, shared with ring group, queue, paging zone, page and shared inbox numbers ([RING_GROUPS_QUEUES.md](RING_GROUPS_QUEUES.md), [PAGING_RECORDINGS.md](PAGING_RECORDINGS.md)) |
| `display_name` | Shown in the interface and used as the default caller ID name |
| `endpoint_name` | The SIP user name, `<organization slug>-<number>` (for example `example-1001`). Generated, globally unique, follows the number when an extension is renumbered. Registers from one phone unless several registered devices carry the extension ([DEVICE_PROVISIONING.md](DEVICE_PROVISIONING.md) §2), then `max_contacts` follows |
| `user_id` | Optional. The user must belong to the same organization |
| `site_id` | Optional site (building); its emergency caller ID is the default for the extension |
| `caller_id_name`, `caller_id_number` | Optional overrides for internal calls (letters, digits and `. ' & ( ) -`; digits with an optional leading `+`) |
| `emergency_caller_id_number` | Optional. Presented on emergency routes (`911`) instead of the regular caller ID: the building's ELIN or registered DID. Wins over the route's and the trunk's numbers ([TRUNKS_ROUTING.md](TRUNKS_ROUTING.md) §7; migration `0010`) |
| `outbound_caller_id_number`, `outbound_caller_id_name` | Optional (Milestone 18, [CALL_FEATURES.md](CALL_FEATURES.md) §3.5). Presented to the carrier on outside calls. The number must be one of the organization's numbers (an inbound route's DID) or on the organization's caller ID allow list, unless the caller holds `routing.write` (`422 caller_id_not_allowed`). An outbound route whose caller ID is marked *force* replaces it; emergency routes present the emergency caller ID. Migration `0033` |
| `is_enabled` | Disabled extensions are kept but left out of the generated configuration |
| `sip_secret_ciphertext`, `sip_secret_changed_at` | The SIP secret, encrypted (§4), and when it was last set |

Changing an extension changes the database only. The engine takes the
change when a configuration revision is generated and deployed
([TELEPHONY_ENGINE.md](TELEPHONY_ENGINE.md) §4). `GET /telephony/engine`
reports `changes_pending: true` from the moment the database differs from
the deployed revision; the Extensions pages show a notice and platform
administrators get an **Deploy changes** button in the top bar
(`POST /telephony/apply`) until the change is deployed.

## 2. Numbering plan

One plan per installation (`system_settings` key `telephony.numbering`,
`GET/PUT /telephony/numbering`, Extensions page → Numbering plan, and the
setup wizard):

| Setting | Default | Meaning |
|---|---|---|
| `extension_length` | 4 | 3 to 6 digits |
| `first_extension`, `last_extension` | 1000, 7999 | Inclusive range, both of `extension_length` digits |
| `reserved_prefixes` | `0`, `9`, `911`, `933` | No extension may start with these: operator, outside line, emergency and the emergency test number |

Rules: numbers are digits only, of the configured length, inside the range,
and not reserved. Feature codes start with `*` (`*43` echo test, `*60`
speaking clock, `*95` record a prompt, `*97` own voicemail, `*98` any
voicemail box; see [VOICEMAIL_IVR.md](VOICEMAIL_IVR.md)) and never
collide. `GET /extensions/next-number[?after=]` suggests the lowest free
number; the "Suggest next free" button in the interface uses it.

**Numbers are unique per organization** (since Milestone 14,
[MULTI_TENANCY.md](MULTI_TENANCY.md) §3): ring groups, queues, paging zones,
pages and shared inboxes take their numbers from the organization's space
(`409 number_in_use` names what holds the number), and each organization's
phones dial in its own context, so two organizations can both have 1001.
`next-number` takes `?organization_id=` (default: the caller's home
organization). The generator refuses a snapshot with a duplicate number in
one engine namespace as a second line of defence. Changing the plan never touches existing extensions; it applies to
new and renumbered ones.

## 3. SIP credentials

* The secret is **generated by the server** when an extension is created:
  24 letters and digits (about 143 bits). Nobody chooses it, and it is never
  sent in the create response.
* `GET /extensions/{id}/sip-credentials` returns the user name, the secret
  and the SIP ports from the SIP settings. It needs `extensions.write` and
  writes an `extension.secret_reveal` audit event every time. This is how a
  technician configures a phone by hand until provisioning (Milestone 9).
* `POST /extensions/{id}/sip-credentials/rotate` replaces the secret
  (`extension.secret_rotate`). The phone stops registering until it is
  updated and the configuration is deployed.
* Renumbering changes the SIP user name too, so the phone must be
  reconfigured; the interface says so when saving.
* Deleting an extension removes its row (devices that pointed at it keep
  working as devices with no primary extension); the endpoint disappears at
  the next deployment.

The interface asks for confirmation (typed number) before deleting, and for
confirmation before rotating a secret.

## 4. Secrets at rest: the installation key

Secrets that the server must be able to read (SIP secrets now, TOTP secrets
in Milestone 4b) are encrypted with the **installation key**
([ADR 0014](adr/0014-installation-key.md)):

| | |
|---|---|
| Location | `/etc/veyra/secrets/installation.key` (`VEYRA_INSTALLATION_KEY_FILE`), 64 hexadecimal characters = 256 bits, mode 0640 root:veyra |
| Created by | the installer (`do_secrets`, also run by `upgrade.sh`, never regenerates an existing key); by hand: `sudo veyra installation-key generate` |
| Checked by | `verify.sh` (presence, format, group) and `sudo veyra installation-key check` (prints a 16-character fingerprint, safe to compare between HA nodes) |
| Algorithm | AES-256-GCM, random 96-bit nonce, the *purpose* as associated data; token format `v1:<base64url(nonce ‖ ciphertext ‖ tag)>` |
| Purposes | `extension.sip_secret:<extension id>` and `config_revision.file:<revision id>:<path>`; a ciphertext copied to another row or column does not decrypt |

What is encrypted:

* `extensions.sip_secret_ciphertext`.
* The **sensitive files of configuration revisions**
  (`pjsip.endpoints.conf` once it carries secrets) inside
  `config_revisions.artifacts`: stored as `{"path", "sensitive": true,
  "ciphertext"}` instead of `content`. Non-sensitive files stay readable so
  the history can be inspected in the database. The deployer decrypts when it
  writes the files; the API decrypts only to compute "changed / unchanged"
  for sensitive files and never returns their content.

What the key does **not** protect: the generated files in
`/etc/asterisk/veyra` (`0640 veyra:asterisk`, which Asterisk must read in
clear), and the snapshot in memory while a revision is generated.

Without the key: creating an extension, showing or rotating a secret and
`/telephony/engine` report `installation_key_present: false` / `503
installation_key_missing`; generating a revision that needs a secret
produces a *failed* revision with the reason; the deployer fails such a
revision and restores the previous files. Nothing is silently written in
clear.

## 5. Backups and key loss

The key lives outside the database on purpose: a database dump alone
reveals no SIP credentials, and a copy of `/etc/veyra` alone reveals none
either. **Back up both**, and keep the key backup separate from the
database dump when you can. `upgrade.sh` already archives `/etc/veyra`
(including the key) beside its database dump under `/var/backups/veyra`,
root-only; Milestone 17 adds encrypted off-host backups.

If the key is lost, every SIP secret and every encrypted revision file is
unrecoverable. Recovery is to create a new key (`veyra installation-key
generate --force`), rotate the secret of every extension and reconfigure
the phones. Key rotation without re-encrypting is not supported yet
(planned with the production hardening milestone).

In an HA pair both nodes must hold the same key
([HA_ARCHITECTURE.md](HA_ARCHITECTURE.md) §4).

## 5a. Live state and click-to-dial (Milestone 5)

Every extension response carries `registration: {registered, channels}`
from the engine (null when the engine cannot report), shown as a badge in
the list and on the page. "Call from this phone" on the extension page
(and `POST /calls/originate {extension_id, number}`) rings the phone first
and places the call when it is picked up; users may dial from their own
extensions, administrators from any extension in their organizations.
Until trunks exist the dialplan reaches internal numbers and feature codes.

## 6. Permissions and scope

| Permission | Default roles | Allows |
|---|---|---|
| `extensions.read` | Organization and site administrators, technicians, read-only users | List, view, search; read the numbering plan; next-number suggestions |
| `extensions.write` | Organization and site administrators | Create, edit, renumber, enable/disable, delete; show and rotate SIP credentials |
| `system.settings.write` | Platform administrators | Change the numbering plan |
| `config.read` / `config.deploy` | Organization administrators / platform administrators | See pending changes / generate and deploy revisions |
| `calls.read` | Organization and site administrators, technicians, read-only users | Active calls of their organizations |
| `calls.originate` | Every role including standard users | Click-to-dial from their own extensions (administrators: any extension they manage) |

Lists and reads are filtered by the caller's organizations; an extension in
another organization answers 404. Creating an extension requires
`extensions.write` in that organization, and inactive organizations refuse
new extensions.

## 7. API summary

```
GET    /extensions?q=&organization_id=&limit=&offset=
POST   /extensions                              {organization_id, number, display_name, user_id?, caller_id_name?, caller_id_number?, emergency_caller_id_number?, outbound_caller_id_number?, outbound_caller_id_name?, is_enabled?}
GET    /extensions/next-number?after=
GET    /extensions/{id}
PATCH  /extensions/{id}
DELETE /extensions/{id}                          -> 204
GET    /extensions/{id}/sip-credentials          (audited)
POST   /extensions/{id}/sip-credentials/rotate   (audited)
GET    /telephony/numbering
PUT    /telephony/numbering
```

Errors: `422 number_not_in_plan` (with the rule that failed), `409
number_in_use`, `409 organization_inactive`, `503
installation_key_missing`, `503 secret_unreadable`.

Audit actions: `extension.create`, `extension.update` (with the changed
fields; a renumbering records the old number and endpoint name),
`extension.delete`, `extension.secret_reveal`, `extension.secret_rotate`,
`telephony.numbering_update`. Events on the bus: `extension.created`,
`extension.updated`, `extension.deleted`.

Console: `veyra installation-key generate [--force] [--path]`,
`veyra installation-key check [--json]`.
