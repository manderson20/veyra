## 5. Known limitations

* Extension numbers are unique across the installation, not per
  organization, until Milestone 14 introduces per-tenant dialplan contexts.
* Installation key rotation with re-encryption is not implemented; a lost
  key means rotating every SIP secret (`docs/EXTENSIONS.md` §5).
* The generated files in `/etc/asterisk/veyra` are in clear (Asterisk reads
  them), protected by `0640 veyra:asterisk`.
* Sites and departments exist in the schema but have no API or UI yet, so
  extensions cannot be attached to a site (site-scoped roles therefore do
  not see extensions; organization-scoped roles do).
* `changes_pending` is computed by regenerating the configuration on each
  engine status request (cheap at this scale; cached later if needed).
* Registration status per extension arrives in Milestone 5.
* SIP user names embed the organization slug (`<organization slug>-22214`
  on dev1). They work, but are long to type into a phone by hand; a
  shorter per-organization endpoint prefix can be added if wanted, and
  provisioning (Milestone 9) removes the typing altogether.

## 8. Proposed Milestone 4b (approved 2026-10-12)

Multi-factor authentication as designed in `docs/MFA_DESIGN.md` and ADR
0012: TOTP enrolment and verification with a pre-authentication session at
sign-in, recovery codes (Argon2id-hashed), per-role policy with a grace
period, administrator reset, console reset for the recovery administrator;
TOTP secrets encrypted with the installation key from this milestone.
Milestone 5 (SIP registration and internal calling) follows.
